# 意思決定の記録手順

セッション中に技術的な意思決定をしたら、その経緯を作業中のリポジトリに1件1ファイルで残す。リポジトリがすでに意思決定の置き場所を持っていればそこへ、無ければ `docs/decisions/` へ書く。後から「なぜこうなっているのか」を読み返せるようにするのが目的。

## 1. 記録するかを判断する

次のどれかに当たるときに記録する。

- **技術選定**: ライブラリ、フレームワーク、ツールを選んだ
- **設計判断**: アーキテクチャ、データ構造、責務の分け方を決めた
- **実装方針**: 実装のアプローチやアルゴリズムを、代替案と比べて決めた
- **規約**: 命名やコードスタイルなど、以後の変更が従う決まりを作った
- **見送り**: 検討した案を採用しないと決めた

次のときは記録しない。

- 比べた案が無く、選択の余地が無かった
- 命名の微調整やtypo修正のように、理由を読み返す必要の無い判断
- 既存の記録と同じ判断を繰り返しただけ
- まだ結論が出ていない。結論が出た時点で記録する

プランモード中はファイルを書けないので、プランの承認後に記録する。

## 2. 出力先を決める

`git rev-parse --show-toplevel` でリポジトリのルートを取り、次の順に探す。リポジトリの外ではカレントディレクトリを起点にする。

1. **規約での指定**: `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`README.md`、`docs/README.md` に意思決定やADRの置き場所が書かれていれば、それに従う。`Grep` で `ADR`、`decision`、`意思決定` を探す
2. **adr-toolsの設定**: ルートに `.adr-dir` があれば、その中身のパスを使う
3. **既存のディレクトリ**: `Glob` で次を探し、Markdownのファイルが入っているものを使う
   - `docs/decisions/`、`docs/adr/`、`docs/adrs/`、`docs/architecture/decisions/`、`docs/design-decisions/`、`doc/adr/`、`doc/decisions/`、`adr/`、`decisions/`
   - 見つからなければ `**/adr/`、`**/decisions/` まで広げる。`node_modules/` や `vendor/` のような依存の中は除く
4. **どれも無い**: `docs/decisions/` を `mkdir -p` で作る

候補が複数見つかったら、ファイルが多く更新日時が新しい方を使い、どれを選んだかを結果の報告で伝える。モノレポでパッケージごとに置き場所があるときは、判断が影響するパッケージのものを使う。

## 3. 既存の書式に合わせる

出力先にファイルがあれば、新しいファイルを書く前に数件を読み、次をそちらに揃える。手順5のファイル名と雛形は、既存の記録が無いときの既定にすぎない。

- **ファイル名**: `0001-use-postgres.md` のような連番なら、最大の番号に1を足して同じ桁数で付ける。日付始まりなら日付で付ける
- **雛形**: 出力先やその近くに `template.md` や `0000-*.md` のような雛形があれば、それを使う。無ければ既存の記録の見出し構成と言語に合わせる
- **ステータスの語**: `Accepted` / `Superseded` のような既存の語をそのまま使う
- **索引**: `README.md` や `index.md` に記録の一覧があれば、新しい記録の行を足す

同じ判断の記録があれば新しく作らず、そのファイルを更新する。前の判断を覆した場合は、古いファイルのステータスを置き換え済みにし、新しいファイルへのリンクを足す。

## 4. 根拠を集める

- 会話の中で挙がった案、比べた観点、ユーザーの発言を拾う
- コードを変えていれば `git status`、`git diff`、`git diff --cached`、`git log --oneline -20` で影響範囲を確かめる

## 5. ファイルを書く

既存の記録が無いときの既定。ファイル名は `YYYY-MM-DD-<判断の内容を表す英語のケバブケース>.md`。日付は `date +%Y-%m-%d` で取る。

```markdown
# （判断のタイトル）

- **日付**: YYYY-MM-DD
- **カテゴリ**: 技術選定 | 設計判断 | 実装方針 | 規約 | 見送り
- **ステータス**: 決定済み | 置き換え済み

## 背景

（なぜこの判断が必要になったか）

## 検討した選択肢

1. （選択肢A）: 利点 / 欠点
2. （選択肢B）: 利点 / 欠点

## 決定

（何を採用したか）

## 理由

（その選択肢を選んだ決め手）

## 影響範囲

（この判断が影響するファイルやコンポーネント。リポジトリ相対のパスで書く）

## 関連

（参照したドキュメント、Issue、PR。無ければ節ごと省く）
```

## 6. コミットする

書いた記録は、ほかの変更と混ぜずに単独でコミットする。

```bash
git add -- <作成・更新したファイル>
git commit -m "docs(decisions): <判断のタイトル>" -- <作成・更新したファイル>
```

- パスを `--` の後ろに並べ、記録のファイルだけをコミットする。ユーザーがステージしている別の変更を巻き込まない
- 索引ファイルを更新した場合や、置き換えた古い記録のステータスを書き換えた場合は、それらも同じコミットに含める
- コミットメッセージは `git log --oneline -10` で既存の書き方を見て、そちらに揃える
- pushはしない
- 次のときはコミットせず、ファイルを残したまま理由を報告する
  - マージ・リベース・cherry-pickの途中（`git status` に表示される）
  - リポジトリの外で記録した
  - コミットが失敗した（pre-commitフックで落ちたなど）。フックを飛ばして通さない

## 7. 結果を伝える

作成または更新したファイルのパス、コミットしたかどうかと、記録した判断の1行要約を伝える。出力先を既存の置き場所から選んだときは、その根拠（規約の記載、`.adr-dir`、既存のディレクトリ）も1行添える。作業の流れを止めないよう、報告は短くする。

## ルール

- 会話やコードで確かめられる事実だけを書く。議論していない案や理由を補わない
- 「検討した選択肢」には、実際に挙がった案だけを書く
- 秘匿情報や絶対パスを書かない。絶対パスにはユーザー名が入る
- 既存の記録が無ければ日本語で書く（ファイル名のトピック部分のみ英語）。既存の記録があればその言語に合わせる
- コミットするのは記録のファイルだけ。pushはしない
