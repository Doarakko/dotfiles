# 実装時のテスト追加

実装を終えたターンの中でテストまで書く。次のターンや別のコマンドへ先送りしない。

## 1. 対象の判定

同一ターンで実装したものを対象にする。後から明示的に起動されて対象が分からない場合は、`git status --porcelain` と `git diff --name-only HEAD` で変更ファイルを取得して対象にする。

変更したもののうち、次はテストを書く。

- 公開関数・公開メソッド・クラス
- 分岐や計算を持つロジック
- 修正したバグの再現条件

次は書かない。

- 設定ファイル、ドキュメント、型定義だけの変更
- プライベート関数・内部ヘルパー（公開関数を通して検証する）
- 委譲するだけの薄いラッパー
- フレームワークが保証する自明な振る舞い

対象外と判断したものがあれば、その理由を最終応答に残す。黙って飛ばさない。

## 2. テスト基盤の確認

既存のテストファイルを Glob で探し、実行コマンドを集める。

- `package.json` の `scripts`
- `Makefile`、`Taskfile.yml`、`justfile`
- `go.mod`、`pyproject.toml`、`tox.ini`、`noxfile.py`

### 基盤が無い場合

勝手にテストフレームワークを導入しない。AskUserQuestion でその場で確認する。探した場所と見つからなかったものを質問文に含め、次から選ばせる。

- **導入してテストを書く**: 言語に応じた既定を提案する。Go は標準の testing、Python は pytest、TypeScript/JavaScript は既存のツールチェーンに合わせる
- **今回は書かない**: 理由を最終応答に残して終える
- **手動テストの手順だけ残す**: 再現手順を書き出して終える

「導入してテストを書く」を選ばれたら、依存の追加と設定ファイルの作成まで行い、手順4で実行できる状態にする。

この確認は、ユーザーとの対話の中で実装しているときにだけ出す。`/pr-fix`、`/ci-fix`、`/pr-create` のような自動化コマンドの実行中、レビュー指摘の自動修正中、呼び出し元から自動化文脈だと伝えられた場合は確認を出さない。テスト基盤が無い旨を報告して手順5へ進む。

## 3. テストの作成

対象が1〜2ファイルなら、このセッションで直接書く。実装の意図を持ったまま書ける方が質が高い。

3ファイル以上なら `doarakko-config:test-generator` を1メッセージ内で並列起動する。各エージェントへは次を渡す。エージェント側の本文はこのセッションからは読めないため、書き方は必ずプロンプトへ含める。

- 対象ファイルのパス
- その変更で何を実現したか
- 手順2で確定したテストフレームワークと実行コマンド
- 下記の書き方

同じ既存テストファイルへ追記することになる対象は、1つのエージェントへまとめる。並列に追記させると後勝ちで消える。

### 書き方

どちらの経路でも次に従う。

1. 既存のテストファイルを Glob/Grep で探し、書き方・配置・命名の規則を読み取る
2. テストファイル名と配置先をその規則に合わせる。既存ファイルへ足す場合は Edit で追記し、上書きしない
3. リポジトリが使っているテストフレームワークに合わせる。新しいものを持ち込まない
4. テストの内容は `doarakko-config:test-review` の基準に従う。バグ修正では、修正前に落ちて修正後に通るテストにする

## 4. 実行して通す

手順2で集めたコマンドでテストを実行する。落ちたら、実装とテストのどちらが誤っているかを判断してから直す。テストの方を期待値に合わせて書き換えて通すのは、実装が正しいと確認できたときだけにする。

## 5. 完了条件

テストを追加して通るまで終わらせない。例外は次の3つだけで、いずれも理由を最終応答に明示する。

- 手順2でユーザーが「今回は書かない」「手動テストの手順だけ残す」を選んだ
- 自動化文脈で起動し、テスト基盤が無かった（確認を出せないため。フレームワークを無断で導入しない）
- 外部依存が重くテストに落とせない（何が障害かを書く）
