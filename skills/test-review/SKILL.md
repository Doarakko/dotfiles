# テストレビュー基準

テストコードレビュー時に以下の観点でチェックを行う。行の網羅率ではなく、振る舞いが守られているかを見る。100%の網羅を求めない。

## 重要度の点数

足りないテストや直すべきテストには、1〜10の点数を付ける。

| 点数 | 基準 |
| --- | --- |
| 9〜10 | 壊れるとデータの消失、セキュリティ事故、システム停止につながる |
| 7〜8 | 壊れると利用者に見えるエラーになる業務ロジック |
| 5〜6 | 壊れると混乱や軽微な不具合になる境界条件 |
| 1〜4 | 網羅のための追加 |

報告するのは5以上だけ。8以上は必須、5〜7は検討として分ける。各指摘には、そのテストが捕まえる失敗の具体例を添える。既存のテストや結合テストがすでに覆っていないかを確かめてから点数を付ける。

## 足りないテスト
- 新しい振る舞いに対するテストの有無
- エラー処理の経路のテスト。ここが無いと失敗が黙って通る
- 境界値と空の入力
- 検証ロジックの異常系（受け付けてはいけない入力が弾かれるか）
- 認証・認可の分岐
- 並行処理や非同期の振る舞い（該当する場合）

## テストの質
- 実装の詳細ではなく、振る舞いと契約を確かめているか
- 意味のある回帰を捕まえられるか。テストを壊すような変更を入れたとき、実際に失敗するか
- 妥当なリファクタリングで壊れないか
- 何を確かめているかがテスト名と本文から読めるか

## 過剰なテストの検出
- 実装の詳細に依存しすぎたテスト（脆弱なテスト）
- 重複したテストケース
- 価値の低いテスト（ロジックの無いgetterやsetterなど、自明な処理のテスト）
- メンテナンスコストが高すぎるテスト
- 不要にモックが多すぎるテスト

## モックとテストデータ
- 外部依存のモック化
- テスト環境の分離（テスト同士が状態を共有していないか）
