# 黙った失敗のレビュー基準

失敗したのに誰にも気づかれないまま処理が進む箇所を探す。気づかれない失敗は、原因から遠い場所で別の不具合として現れ、調べるのに時間がかかる。

## 先にプロジェクトの方針を確かめる

握りつぶしが正しい場面もある。通知やメトリクス送信のような副次的な処理の失敗で本体を止めない、などの方針がプロジェクトにあるかを、`coding-style-guide-review`と同じ探索先（`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`など）で確かめる。

- 方針に沿っていて、理由がコメントに書かれている握りつぶしは指摘しない
- 方針はあるが理由が書かれていない箇所は、Lowで「理由をコメントに残す」とだけ指摘する

## 探す箇所

- 空のcatch / except / rescue、`|| true`、`2>/dev/null`で終了コードまで捨てている箇所
- ログを出すだけで処理を続けているcatch
- 失敗時に既定値・null・空配列を返し、呼び出し元が成功と区別できない箇所
- `?.`やnull合体演算子で、失敗しうる処理を黙って飛ばしている箇所
- 理由の説明が無いまま、別の手段を順に試す代替処理
- 回数を使い切っても誰にも伝えないリトライ
- 本番のコードがモックやスタブへ切り替わる代替処理
- 範囲が広すぎるcatch。想定外の例外まで飲み込む

## 箇所ごとに問うこと

- **範囲**: 捕まえる例外は想定したものだけか。このcatchが飲み込みうる想定外のエラーを具体的に挙げる
- **伝わり方**: 失敗はログ・終了コード・戻り値・利用者向けのメッセージのどれかで外へ出るか。出ないなら誰が気づくのか
- **代替処理**: 失敗時の別の振る舞いは仕様として決められたものか。利用者は、エラーではなく代替の結果を見ていることに気づけるか
- **伝播**: ここで捕まえずに上位へ渡すべきではないか。捕まえたせいで後始末が漏れていないか
- **倒す向き**: 値が読めない・判定できないとき、安全な側（処理を止める、全体を対象にする）へ倒しているか。黙る側へ倒していないか

## 重要度

| 重要度 | 例 |
| --- | --- |
| Critical | データの欠落やセキュリティ判定の素通りにつながる握りつぶし |
| High | 空のcatch、想定外の例外まで飲み込む広いcatch、仕様に無い代替処理 |
| Medium | ログはあるが文脈が足りず、後から原因を追えない |
| Low | 方針どおりの握りつぶしだが理由が書かれていない |

指摘には、飲み込まれうるエラーの種類と、修正後のコードの形を添える。
